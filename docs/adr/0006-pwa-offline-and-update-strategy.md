# ADR 0006: PWA, offline caching, and update strategy

- Status: Accepted
- Date: 2026-11-13

## Context

OpenNest is a local-first Next.js App Router application. User content lives in
IndexedDB through the Dexie adapter and the app has no server API in the browser
stage. The remaining gap is the installable shell: without a service worker, a
reload with no connection fails before the local data layer can run.

The solution must not cache private responses indiscriminately, must not clear
user data when a new version activates, and must not force a reload while a note
is being edited.

## Decision

Use a small hand-written service worker instead of adding a PWA framework. Keep
the worker in `scripts/pwa/service-worker.js` and generate the deployable
`apps/web/public/sw.js` after every production build.

The build scans `.next/static`, the six shell routes (`/`, `/library`, `/notes`,
`/search`, `/settings`, `/offline`), the manifest, icons, favicon, and public
assets. It injects a cache version derived from the Next build ID, the worker
template, and the precache list. The generated worker is a gitignored build
artifact.

Caching rules:

- Install calls `cache.addAll` with `cache: "reload"` for the complete shell. A
  missing required asset fails the install rather than shipping a partial
  offline experience.
- Full navigations are network-first with a four-second timeout. On failure the
  worker returns a cached copy of the same path, then the precached `/offline`
  document.
- `/_next/static`, icons, and the favicon are cache-first and immutable.
- Next RSC requests are network-first and use a cached response when offline.
- Non-GET, cross-origin, range, authorized, `/api/`, `/_next/image`, `sw.js`, and
  manifest requests bypass the worker. Responses carrying `no-store` or
  `private` are not stored.
- Activate removes only caches with the `opennest-` prefix. It never touches
  IndexedDB or any other browser storage.

Update rules:

- A new worker installs and waits. It does not call `skipWaiting` during install.
- When a waiting worker exists and the page already has a controller, the shell
  shows a localized update prompt.
- Only the user's `Refresh` action posts `SKIP_WAITING`. The reload happens after
  `controllerchange`, not before.
- A first install calls `clients.claim()` so the current page becomes controlled
  without a prompt or reload.

`next.config.ts` marks `/sw.js` as non-cacheable and allows root scope. The
manifest is generated by `apps/web/app/manifest.ts`.

## Consequences

- The shell, cached routes, and locally stored content survive offline reloads.
- A first visit without a network still cannot load the app, because no worker
  or cache exists yet.
- Dynamic routes are only offline-ready after a prior online visit.
- The worker depends on a production build step. Serving `.next` directly
  without running `scripts/pwa/build.mjs` leaves no `sw.js`.
- The deployment must use HTTPS (or localhost) and must not put a long-lived CDN
  cache in front of `sw.js`.
- Offline client prefetches may produce expected network errors in the console;
  tests distinguish those from application errors.
- Browser storage eviction remains possible, so backup export is still required
  for data durability.

## Alternatives considered

- `next-pwa` or Workbox: adds a dependency and generated runtime for a small,
  auditable cache policy. The project already has a build script and E2E harness.
- Cache-first navigations: faster repeat loads but risks showing stale HTML and
  makes deployment updates harder to reason about.
- Automatic `skipWaiting`: shortens the update path but can reload the page while
  a note is autosaving, which violates the editing guarantees.
- No service worker: keeps the code smaller but leaves the app unusable offline
  even though its data is already local.
