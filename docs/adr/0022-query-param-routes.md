# ADR 0022: Query-parameter routes for static export

- Status: Accepted
- Date: 2026-11-21
- Context: Android static export in ADR 0021
- Related: ADR 0004, ADR 0021
- Product conflict: none; the web routes remain shareable and the old URLs
  redirect

## Context and problem

The current detail views use dynamic path segments:

- `/notes/[noteId]`
- `/library/[folderId]`
- `/files/[fileId]`
- `/extensions/[extensionId]`

Next.js can prerender these when their ids are known at build time, but note,
folder, file, and extension ids are created locally at runtime. A static export
cannot generate a page per runtime id. Capacitor's local server also has no
application router that can map an unknown path to a dynamic Next.js page.

The app needs detail views that work from a static file bundle, keep browser
history and shareable URLs, and do not duplicate the web UI or data layer.

## Decision

Keep four static list pages and move the selected entity id into the query
string:

- `/notes?noteId=...`
- `/library?folderId=...`
- `/files?fileId=...`
- `/extensions?extensionId=...`

The pages stay static. A small client route component reads `useSearchParams`
inside a `Suspense` boundary and renders either the list or the detail view. The
detail component is keyed by the selected id so switching records remounts its
local state. Ids are encoded with `encodeURIComponent` through shared helpers in
`apps/web/lib/routes.ts`.

The PWA precaches the four static pages. A query string resolves to the same
cached shell, so detail views keep working offline after the page shell and the
local data are available.

Old dynamic paths are redirected on the client to the new query route. The
redirect helper is also used by the error page. In the Android WebView, an old
path that is served as the root document is still redirected when its pathname is
preserved; a cold reload of an old dynamic path is not guaranteed.

## Alternatives considered

1. Generate every possible detail page at build time. Rejected because ids are
   created locally and are not known to the build.
2. Keep dynamic routes and use a custom server inside the APK. Rejected because
   it adds a server runtime to a local-first bundle and does not remove the
   static export constraint for the PWA.
3. Hash routing such as `/#/notes/<id>`. Rejected because it changes the
   existing URL model and makes search-parameter state harder to combine.
4. Encode the selected id in a path file with a rewrite rule. Rejected because
   static hosts and the Capacitor local server do not share a rewrite contract.
5. Use query parameters on static pages. Recommended because it works on the
   web, in the PWA cache, and in the APK with no server rewrite.

## Consequences

- Detail URLs are shareable and survive reloads on the web and on static hosting.
- The route-level metadata is page-level only; per-detail titles are no longer
  generated by the server.
- The list and detail views share one page bundle, which is slightly larger than
  a list-only page.
- The selected entity is not part of the pathname, so pathname-only navigation
  highlighting still treats the section as active.
- Old dynamic URLs redirect with client-side JavaScript; search engines and
  no-JavaScript clients see the error page instead of a redirect.
- The extension sandbox and all data access remain unchanged; only the route
  transport changes.
- ADR 0004's statement that the active folder is a dynamic route is superseded
  for the current implementation; its data-flow decision is unchanged.
