# Sync-compatible data model

## Scope

Local-only D2. No network code, server, authentication, device trust, or global revision authority. D2 makes no global order claim across devices.

## Implementation surface

- `packages/sync/src/`: sidecar types, `SyncStore`, policy, `SyncError`, canonical JSON and SHA-256, the recorder, the merge helpers, and the memory harness.
- `packages/storage-dexie/src/{schema,storage,sync-store}.ts`: Dexie engine schema version `4` and decimal `SCHEMA_VERSION` `3`.
- `packages/storage-sqlite/src/{schema,storage,sync-store}.ts`: Drizzle schema and adapter wiring.
- `packages/storage-sqlite/migrations/0002_sync_sidecars.sql` and `0003_sync_high_water.sql`: sidecar schema, outbox high-water backfill, indexes, and journal entries at indexes `2` and `3`; the migration count is now `4`.
- `packages/storage-conformance/src/scenarios/sync.ts`: shared scenarios run against Dexie and SQLite (`:memory:` and file).

Both adapters create the seven sidecars, bootstrap one installation device, and backfill existing rows with `originDeviceId = "legacy"`, `entityRevision = 1`, and `workspaceRevision = 0`. Initialization replaces the legacy origin with the installation device and rewrites the legacy metadata. Every subsequent local write records entity metadata, field metadata, tombstones, and optionally an outbox row in the same transaction as the entity write.

## Sidecar tables

- `sync_meta`, primary key `(workspaceId, entityType, entityId)`.
- `sync_field_meta`, primary key `(workspaceId, entityType, entityId, fieldPath)`.
- `sync_outbox`, primary key `opId`, unique `(workspaceId, deviceId, localSequence)`.
- `workspace_sync_state`, primary key `(workspaceId, deviceId)`; `lastLocalSequence` is the outbox high-water mark.
- `sync_tombstone`, primary key `(workspaceId, entityType, entityId)`.
- `sync_conflict`, primary key `conflictId`.
- `sync_devices`, primary key `(workspaceId, deviceId)`.

## Device identity

One device ID per installation, generated by the adapter, stored in sync_devices, excluded from backups.

## Revisions

entityRevision and fieldRevision are local monotonic counters. workspaceRevision increments once per write transaction per workspace and is local only. The transaction context stores revisions in a map keyed by workspace, so a transaction that writes two workspaces keeps each counter independent.

## G-12-1 outbox

Disabled by default. When enabled, `maxRows` caps all outbox rows and the 30-day retention window prunes acknowledged rows. Pending or failed rows are never silently dropped. A full outbox throws `outbox_full` and rolls back the entity write. Recording is idempotent by `opId`: a replayed operation is skipped and returns the current revision. `localSequence` is unique and monotonic per workspace and device, starts at 1, and may repeat for the same device in another workspace. It is allocated from `workspace_sync_state.lastLocalSequence`, so deleting or pruning rows cannot reuse a value. `appendOutbox` is insert-only; a duplicate `opId` is rejected with `invalid_sync_state`. The outbox stores immutable field patches, never a second copy of the entity or file bytes.

The high-water mark is backfilled from `MAX(localSequence)` during migration and preserved across restore.

## G-12-2 tombstones

Tombstones are written on delete. Compaction and automatic stale marking are disabled. tombstoneFloor starts at zero. A write to an entity with any tombstone row, active or compacted, is rejected.

## G-12-3 merge-safe fields

Exactly note.pinned and tag.color. All other synced fields are content-bearing.

## Relation arrays

tagIds and targetNoteIds are canonical ID arrays: dedupe, then ascending code unit order by raw ID string using the default sort(), never localeCompare. Product order has no meaning. Field patches, hashing, storage, and conflict comparison use the canonical form, so different input order cannot create a false conflict.

## G-12-4 conflicts

No user-facing conflict UI in D2. Records preserve local and remote values. The store can list conflicts and mark local or remote resolutions. Applying a resolution to entity state is deferred with the conflict UI. merged and copy resolutions are typed but return unsupported_resolution until the sync UI gate.

## G-12-6 ordering

updatedAt, then originDeviceId, then opId. No HLC. A merge-safe conflict may pick a winner under skew. A content-bearing conflict always preserves both values.

## Operation hashing

payloadHash is SHA-256 over canonical JSON of the stable envelope: opId, workspaceId, entityType, entityId, operation, and fieldPatches. Base revisions are stored metadata and are not hashed, because Dexie cannot await crypto inside a transaction.

## Operation timestamps

create uses the caller's at. update uses the effective core timestamp, `laterOf(at, previous.updatedAt)`, so sync metadata never moves backwards. Tag update uses patch.at because tag rows have no updatedAt. setTags, setLinks, and delete use one new Date().toISOString() per operation. Core ports do not change.

## Transaction revisions

The first recorded write in an outer storage transaction allocates one workspaceRevision per workspace; every later write in that transaction reuses it for the same workspace. Writes outside an outer transaction allocate their own revision. A recorder batch holds one workspace; a batch spanning workspaces is rejected with invalid_sync_state. SQLite serializes nested savepoint writes within an outer transaction so concurrent nested writes cannot release each other's savepoints.

## Backup and restore

Backup v1 is unchanged and excludes all seven sidecars: `sync_meta`, `sync_field_meta`, `sync_outbox`, `workspace_sync_state`, `sync_tombstone`, `sync_conflict`, and `sync_devices`. It also excludes device IDs and install identity. A v1 snapshot without sidecars is still accepted; restore clears stale sidecars in the same transaction, preserves the installation device ID by recreating its device row, keeps the target workspace's outbox high-water mark, and backfills restored entities with the installation `originDeviceId`, `entityRevision = 1`, and `workspaceRevision = 1`. The migration backfill is different: it writes `originDeviceId = "legacy"` and `workspaceRevision = 0`, then bootstrap rewrites the legacy origin to the installation device.

Restore is blocked when `workspace_sync_state.remoteWorkspaceId` is non-null. Dexie checks this inside the restore transaction before clearing anything. SQLite checks before writing any blob and rechecks inside the database transaction, so a blocked restore leaves existing blobs unchanged. The failure is `remote_target_present`. A future remote writer could still race the pre-check between the guard and the blob writes; the in-transaction recheck limits that window.

## No global order

`workspaceRevision` is local to this device. D2 does not claim a cross-device revision order, a server cursor, or distributed tombstone authority. Future sync needs a canonical authority or a per-device vector; local-only behavior must not be described as globally ordered.

## Data classification

sync_meta, sync_field_meta, sync_devices, workspace_sync_state, and sync_tombstone are metadata. Outbox patches and conflict values inherit the content data class. File bytes are never stored in sidecars.

## Known limitations

An interrupted SQLite restore can leave orphan blob files. Blobs are written before the database transaction. If the database transaction fails, newly written blobs are deleted; if the restore succeeds, orphans are purged. A blob-write failure in the middle of the loop or a process crash can still leave orphans, so cleanup remains backlog. An interrupted blob write can also leave a `.tmp` file that `purgeOrphans` does not remove.

The 2026-11-15 audit blockers in ADR 0012 are fixed. A follow-up audit fixed the compacted-tombstone write gap and added revoked-device, up-to-date-floor, and compacted-tombstone regression coverage. Remaining limitations are the orphan blob and temp-file backlog above and the narrow SQLite restore race between the pre-check and blob writes.
